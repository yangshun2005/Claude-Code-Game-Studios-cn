# Agent 测试规范：engine-programmer

## Agent 摘要
领域：渲染管线、物理集成、内存管理、资源加载和核心引擎框架。
不负责：游戏玩法机制（gameplay-programmer）、构建基础设施（devops-engineer）、编辑器/调试工具 UI（tools-programmer）。
未分配门禁 ID。

## 测试用例

### 用例 1：域内请求 — 输出恰当
**输入：**"为投射物实现一个自定义对象池，避免每帧分配。"
**预期行为：**
- 产出引擎级对象池实现，带 acquire/release 接口
- 池按投射物对象类型定型，使用预分配的固定大小存储
- 提供线程安全说明（或明确标记为仅单线程并给出理由）
- 按编码规范为公共 API 添加文档注释
- 输出与项目配置的引擎和语言兼容

### 用例 2：域外请求 — 正确重定向
**输入：**"给玩家控制器添加蹬墙跳能力。"
**预期行为：**
- 不产出蹬墙跳玩法代码
- 明确说明玩法功能属于 `gameplay-programmer`
- 将请求重定向至 `gameplay-programmer`
- 若提供该能力可调用的引擎级查询（如墙面接触和表面法线），该 API 不依赖玩法代码（严格依赖方向）

### 用例 3：内存泄漏诊断
**输入：**"每次关卡加载内存增长约 50MB 且从不释放。我们怀疑是资源加载系统。"
**预期行为：**
- 先测量再改代码：记录内存基线、重复加载/卸载循环、数据（改前改后 profile）
- 审计其负责的资源加载/缓存和对象生命周期代码，查找从未释放的引用，指出可能原因（孤立的资源句柄、循环引用、从不淘汰的缓存）
- 针对识别出的泄漏模式给出具体修复
- 提供验证修复的测试（加载前内存基线、卸载后测量、确认回到基线）

### 用例 4：跨域协调 — 共享系统优化
**输入：**"我需要优化物理 broadphase，但玩法系统与物理查询 API 紧密耦合。"
**预期行为：**
- 不单方面更改物理查询 API 表面（会破坏 gameplay-programmer 的代码）
- 与 `lead-programmer` 协调，安全规划变更
- 提出迁移路径：新优化 API 与旧 API 并存，设弃用期
- 在继续前记录协调要求

### 用例 5：上下文传递 — 检查引擎版本参考
**输入：**上下文中提供引擎版本参考（Godot 4.6）。请求："为项目设置默认物理引擎。"
**预期行为：**
- 读取引擎版本参考，指出 Godot 4.6 变更：Jolt 物理现为默认
- 产出考虑 Jolt 成为默认的配置指导（4.6 迁移说明）
- 指出 `docs/engine-reference/godot/modules/physics.md` 记录的 GodotPhysics3D→Jolt 差异 — HingeJoint3D 的 `damp` 在 Jolt 下不支持、碰撞边距行为可能不同、Jolt 在运行时对不支持的属性发出警告 — 且现有项目保留当前引擎设置；说明参考文档未列出其他 API 差异，而非杜撰
- 不建议已弃用或 4.6 之前的物理设置步骤，除非注明适用于旧版本
