# Agent 测试规范：network-programmer

## Agent 摘要
领域：多人网络、状态复制、延迟补偿、匹配协议设计、网络消息 Schema。
不负责：游戏玩法逻辑（仅负责其网络部分）、服务器基础设施与部署（devops-engineer）。
未分配门禁 ID。

## 测试用例

### 用例 1：领域内请求 — 输出恰当
**输入：**“为 4 人合作游戏设计玩家位置的状态复制。”
**预期行为：**
- 产出同步策略文档，涵盖：
  - 复制频率（例如 20Hz，配合增量压缩）
  - 优先级分层（例如 自身玩家高优先级，其他玩家中优先级）
  - 远程玩家的插值方案（例如线性插值，100ms 缓冲）
  - 每玩家每秒带宽估算
- 不实现玩家移动逻辑本身（交由 gameplay-programmer）
- 提出航位推算或预测策略以减少可见延迟

### 用例 2：领域外请求 — 正确重定向
**输入：**“把我们的游戏服务器部署到 AWS EC2 并配置自动扩缩容。”
**预期行为：**
- 不产出服务器部署配置、Terraform 或 AWS 搭建脚本
- 明确说明服务器基础设施属于 `devops-engineer`
- 将请求重定向至 `devops-engineer`
- 若提供任何部分，仅限于服务器构建所需的网络侧契约（协议、消息版本管理、连接生命周期）— 不含部署、托管或扩缩容配置

### 用例 3：状态分歧 — 回滚/对账
**输入：**“高延迟下，客户端物理对象状态与权威服务器状态出现分歧。”
**预期行为：**
- 提出回滚并对账的方案（客户端预测 + 服务器权威校正）
- 明确状态快照格式、对账触发阈值（例如位置误差 >5 单位）、校正插值速度
- 保留客户端未确认的输入，并在每次服务器校正之上重新应用（即“客户端本地预测、与服务器对账”中对账的那一半）
- 不修改物理模拟本身（非网络代码）— 记录模拟必须暴露的接口契约（状态快照、校正入口），并在改动该系统前先询问（“这需要改动 [其他系统]。我是否应先与那边协调？”）

### 用例 4：反作弊冲突
**输入：**“我们想要客户端权威位置以获得流畅移动，但反作弊要求服务器校验。”
**预期行为：**
- 指出直接冲突：客户端权威快但可被利用；服务器权威安全但需要延迟补偿
- 与 `security-engineer` 协调，就校验边界达成一致
- 提出折中方案（例如服务器在容差范围内校验位置并标记异常值），而非单方面决定
- 记录权衡；若 security-engineer 与 network-programmer 无法达成一致，将最终决定上报 `technical-director`

### 用例 5：上下文传递 — 延迟预算
**输入：**上下文中提供的技术偏好：目标延迟为 95 百分位玩家 80ms RTT。请求：“为格斗游戏设计输入复制方案。”
**预期行为：**
- 在设计里明确引用 80ms RTT 预算
- 选择按该预算校准的复制方案（例如该延迟下格斗游戏优先采用回滚网络代码）
- 根据 80ms 预算计算输入延迟帧数（例如 60fps 下 2 帧 = 33ms 缓冲）
- 指出回滚网络代码需要确定性、可重模拟的游戏状态，并按协调线所命名的角色分流：物理与模拟确定性交由 engine-programmer，回滚重模拟的游戏玩法代码交由 gameplay-programmer

## 协议合规

- [ ] 保持在声明的领域内（复制、延迟补偿、协议设计、匹配）
- [ ] 将服务器部署重定向至 devops-engineer
- [ ] 返回结构化结论（同步策略、协议规范、带宽估算）
- [ ] 不实现游戏玩法逻辑 — 仅为其规定网络契约
- [ ] 与 security-engineer 就反作弊边界协调
- [ ] 按所提供上下文中的明确延迟目标进行设计
- [ ] 写入前询问“我可以将其写入 [filepath] 吗？”并指明文件

## 覆盖说明
- 复制策略（用例 1）应包含可供 technical-director 审查的带宽计算

- 反作弊冲突（用例 4）确认该 Agent 会上报，而非单方面决定安全权衡
