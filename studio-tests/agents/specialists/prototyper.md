# Agent 测试规范：prototyper

## Agent 摘要
- **领域**：在 `prototypes/` 目录中快速构建一次性原型、概念验证实验、机制可行性测试。为追求速度有意放宽标准——原型不是生产代码。
- **不负责**：`src/` 中的生产源代码（gameplay-programmer）、设计文档（game-designer）、生产级架构决策（lead-programmer / technical-director）
- **门禁 ID**：无；原型结论后产出建议文档；不参与阶段门禁

---

## 静态断言（结构性）

- [ ] `description:` 字段存在且领域明确（提及一次性构建 / 概念原型 / 速度优先于标准）
- [ ] `tools:` 包含 Read、Glob、Grep、Write、Edit、Bash（需编写并运行一次性构建），`isolation:` 为 `worktree`——frontmatter 无法将写入限定到某个目录，因此 `prototypes/` 的边界由正文的隔离要求（下一条断言）保证
- [ ] 模型层级为 `sonnet`——frontmatter 的 `model:` 精确为 `sonnet`（层级说明见 `.claude/docs/model-tiers.md`）
- [ ] Agent 定义明确声明原型代码不是生产代码，不得复制到生产代码根目录

---

## 测试用例

### 用例 1：领域内请求——原型化抽牌机制
**输入**："用 2 小时原型化一个抽牌机制。核心问题：每回合抽 3 张牌、手牌上限 7 张，手感好吗？我今天就要在试玩中测试。"
**预期行为**：
- 构建前先陈述可证伪假设（"如果玩家每回合抽 3 张牌、手牌上限 7 张，他们会感到 [Y]——由 [Z] 佐证"）和风险最高的假设
- 推荐原型路径并给出理由——卡牌机制不涉及时机精度问题，应走 HTML 或纸面路径，而非引擎路径
- 用 3–5 条要点提出范围（牌堆、抽 N 张、手牌上限 7、最小状态显示），构建前获得确认
- 输出到 `prototypes/card-draw-concept/`（例如双击即可打开的单个自包含 `prototype.html`，或纸面路径下的 `rules.md` + `play-log.md`）；每个代码文件以 `PROTOTYPE - NOT FOR PRODUCTION` 头开头，注明问题和日期
- 代码速度优先于正确性：无需单元测试、无需文档注释、允许全局状态；不做菜单或打磨
- 不实现生产模式（依赖注入、信号、数据驱动配置），除非不用它们反而更耗时
- 写入前询问"我可以写入 [filepath] 吗？"

### 用例 2：领域外请求——生产级实现
**输入**："抽牌机制原型效果很好。现在为 src/gameplay/cards/ 编写卡牌系统的生产实现。"
**预期行为**：
- 不向 `src/` 写入生产代码
- 明确说明原型代码是一次性的：已验证机制的生产实现需按正式标准从零编写，原型仅作参考
- 指向原型的 `REPORT.md`（假设、结果、建议、发现的调优值、经验教训）作为带入生产的内容——若尚不存在则主动提出编写——传递的是知识而非代码
- 将生产架构问题转交 `lead-programmer`
- 不将原型代码复制到 src/，也不在不警告其非生产质量的情况下建议将其作为起点

### 用例 3：原型验证机制可行——建议输出
**输入**："抽牌原型试玩效果很好。三场测试都喜欢每回合抽 3 张、手牌上限 7。未观察到困惑。下一步？"
**预期行为**：
- 按概念原型报告模板生成 `prototypes/card-draw-concept/REPORT.md`，写入前请求批准
- 报告包含：所测假设、风险最高的假设、结果以具体观察呈现（3 场测试，未观察到困惑）、试玩人数及假设结论 CONFIRMED、**建议：PROCEED** 及相应证据、需保留的调优值（每回合 3 张、手牌上限 7）、经验教训
- 报告写完后更新 `prototypes/index.md`
- 将 PROCEED 作为建议呈现——决定权属于用户 / creative-director，而非 prototyper
- 不开始编写生产代码；指向的下一步是设计工作（GDD），而非实现
- 输出结构为可供决策的建议，而非叙述性总结

### 用例 4：原型揭示机制不可行——放弃说明
**输入**："基于物理的开锁机制原型已完成。4 场试玩后，所有测试者都觉得令人沮丧——精度要求太高，不好玩。一名测试者怒退。"
**预期行为**：
- 按概念原型报告模板生成 `prototypes/lock-picking-physics-concept/REPORT.md`，写入前请求批准
- 报告包含：所测假设、假设结论 REFUTED、具体原因以观察呈现（精度门槛过高、4 场测试均出现负面情绪、怒退事件作为证据）
- **建议：KILL** 物理方案——或仅在给出具体转向方向及保留内容（如简化的钥匙-锁簧或节奏机制）时 PIVOT；绝不 PROCEED
- 不因沉没成本建议坚持原型机制——结论基于证据，而非投入的努力
- 不将结果标记为不确定——4 场测试反应一致负面，证据足以支持决策

### 用例 5：上下文传递——使用项目的引擎脚本语言
**输入上下文**：项目使用 Godot 4.6 与 GDScript（`project.yaml` 中的 `engine.name` 和 `engine.language`）；用户已选择引擎路径。
**输入**："原型化一个基础网格移动系统——玩家点击格子，角色移动到该格。"
**预期行为**：
- 用 GDScript 产出原型——而非 Python、C# 或伪代码
- 使用适合网格的 Godot 4.6 节点类型：TileMapLayer（而非 TileMap，`docs/engine-reference/godot/deprecated-apis.md` 将其列为自 4.3 起已弃用）或自定义网格管理节点，玩家用 CharacterBody2D 或 Node2D
- 不套用生产编码标准（无强制测试覆盖率、无文档注释、允许全局状态）
- 输出到 `prototypes/grid-movement-concept/`，而非 `src/`
- 写完后交回控制权：请用户运行项目并粘贴错误或描述观察结果，而非假定其可用
- 若对某个 Godot 4.6 API 不确定，标注该具体 API 并注明需对照 Godot 4.6 文档核实——`docs/engine-reference/godot/VERSION.md` 通过 `CLAUDE.md` 的导入到达 Agent，其知识缺口警告要求建议 Godot API 调用前先交叉查阅该目录

## 协议合规

- [ ] 保持在声明的领域内（仅 prototypes/ 目录；用于概念验证的一次性代码）
- [ ] 拒绝生产实现请求，说明生产代码从零编写，并指向原型的 REPORT.md 作为交接
- [ ] 原型评估后产出结构化 REPORT.md，附 PROCEED / PIVOT / KILL 建议及证据支撑
- [ ] 不在无明确警告的情况下建议将原型代码以生产形式保留
- [ ] 使用项目配置的引擎和脚本语言；按 `CLAUDE.md` 导入的 `VERSION.md` 中的知识缺口警告标注版本不确定性

---

## 覆盖说明
- 用例 2（生产重定向）至关重要——原型代码泄漏到 src/ 是常见质量问题
- 用例 4（放弃的诚实性）测试 Agent 是否避免沉没成本偏差——失败的原型应干净地放弃
- 用例 5 要求 `project.yaml` 配置了 `engine.name` 和 `engine.language`；未配置则测试不完整。若 `project.yaml` 和 `.claude/docs/technical-preferences.md` 均未指明，预期输出是询问引擎和语言，而非猜测
- 有意放宽编码标准是特性而非缺陷——不要将原型输出中缺少测试或文档注释标记为失败
- 无自动运行器；手动审查或通过 `/skill-test` 审查
