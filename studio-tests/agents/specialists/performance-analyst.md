# Agent 测试规范：performance-analyst

## Agent 摘要
领域：性能分析、瓶颈识别、性能指标跟踪和优化建议。
不负责：实现优化（属于该领域对应的程序员）。
未分配门禁 ID。

---

## 静态断言（结构性）

- [ ] `description:` 字段存在且领域明确（提及性能分析 / 瓶颈分析 / 性能指标）
- [ ] `tools:` 列表包含 Read、Write、Edit、Bash、Glob、Grep
- [ ] 模型层级为 `inherit` — frontmatter 中 `model:` 精确读取为 `inherit`（层级说明：`.claude/docs/model-tiers.md`）
- [ ] Agent 定义不声称有权实现任何优化 — 明确声明自身仅做分析/建议

## 测试用例

### 用例 1：领域内请求 — 输出恰当
**输入：** "分析这组帧时间数据：CPU 14ms，GPU 8ms，物理 6ms，绘制调用 420，脚本 3ms。"
**预期行为：**
- 识别主要瓶颈：帧受 CPU 限制（CPU 14ms vs GPU 8ms）— 在 16.67ms（60fps）帧内，但余量不足 3ms
- 拆解各贡献项：物理（6ms，占 CPU 时间 43%）是首要元凶
- 绘制调用（420）标记为次要问题（若预算上限更低，例如项目 `performance.draw_call_limit` 规定每次 200 绘制调用）
- 生成按优先级排序的瓶颈报告：
  1. 物理 — 6ms，降低模拟频率或切换 broadphase 算法
  2. 绘制调用 — 420，实施批处理或 LOD
  3. 脚本 — 3ms，分析热点路径
- 不实现上述任何优化

### 用例 2：领域外请求 — 正确重定向
**输入：** "实现批处理优化，将绘制调用从 420 降到 200 以下。"
**预期行为：**
- 不产出批处理的实现代码
- 明确声明实现优化属于系统负责人 — `technical-artist`，其渲染优化涵盖批处理（同时点名 `engine-programmer` 也可以，因为批处理需要引擎级渲染改动）
- 将实现重定向给 `technical-artist`，并把建议作为任务简报移交：目标（绘制调用低于 200）、预估影响、实现成本

### 用例 3：回归识别
**输入：** "上周提交后性能显著下降。帧时间从 10ms 升到 18ms。"
**预期行为：**
- 对比窗口前构建（约 10ms）与窗口后构建（约 18ms）的性能分析；若任一构建无分析数据，则请求或提议采集，而非猜测
- 将 8ms 差值定位到增长了的帧时间类别（游戏逻辑、渲染、物理、AI、音频），而非仅凭提交信息或 diff 猜测原因
- 仅在性能分析支持时才点名可疑提交或系统（例如提交范围内的构建分析）— 绝不单凭提交信息或 diff
- 在"自上次报告以来的回归"下报告，附实测差值（10ms → 18ms）和受影响类别，并建议修复负责人而非自行实现修复

### 用例 4：建议与代码质量的权衡
**输入：** "脚本瓶颈最快的优化是内联所有调用并移除抽象层。"
**预期行为：**
- 揭示权衡：内联提升性能但降低可测试性，违反要求公共方法可单元测试的编码标准
- 不在未注明代码质量代价的情况下推荐该优化
- 将权衡上报给 `technical-director`（其汇报对象）决策
- 呈现各选项及其权衡 — 例如仅内联最热的 2–3 个方法，保持公共方法可测试 — 而非全有或全无的单一建议

### 用例 5：上下文传递 — 项目性能预算
**输入：** 上下文中提供的项目配置性能预算（`project.yaml` 中的 `performance.*`）：目标 60fps，帧预算 16.67ms，绘制调用上限 200，内存上限 512MB。请求："审查当前构建的性能分析。"
**预期行为：**
- 引用所提供上下文中的具体数值：16.67ms、200 绘制调用、512MB
- 在其性能报告格式中，逐项将当前测量值与各阈值显式对比（帧时间和内存的预算 / 实际 / 状态表）
- 根据所提供数值将各指标状态标记为 OK 或 OVER
- 不使用与上下文所提供不同的预算数值

## 协议合规

- [ ] 保持在声明的领域内（性能分析、分析、建议 — 而非实现）
- [ ] 将优化实现重定向给系统负责人（渲染优化如批处理交给 technical-artist，引擎系统交给 engine-programmer），而非自行实现
- [ ] 以性能报告格式返回结构化发现（预算/实际/状态表、带影响和建议的首要瓶颈、回归）
- [ ] 将代码质量权衡上报给 technical-director，而非单方面决定
- [ ] 应用所提供上下文中的预算阈值，而非假定的默认值
- [ ] 为每项建议的优化点名应由谁实现（"建议并指派"），而非自行实现
- [ ] 写入前询问"我可以将此写入 [文件路径] 吗？"并指明文件

## 覆盖说明
- 帧时间分析（用例 1）输出遵循该 Agent 的性能报告格式；在 `/perf-profile` 或 `/team-polish` 下运行时，报告写入 `production/polish/`
- 回归用例（用例 3）确认该 Agent 从跨构建的性能分析中定位原因，而非仅测量症状或凭 diff 猜测
- 代码质量权衡（用例 4）验证该 Agent 不会在不标记冲突的情况下推荐违反编码标准的优化
