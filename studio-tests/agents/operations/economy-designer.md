# Agent 测试规范：economy-designer

## Agent 摘要
- **领域**：资源经济设计、战利品表设计、成长曲线（XP、等级、解锁）、游戏内市场与商店设计、经济平衡分析、消耗与产出机制、通胀/通缩风险评估、物品与货币的实体注册表数值
- **不负责**：运营活动排期与结构（live-ops-designer）、核心玩法机制（game-designer）、代码实现、分析埋点设计（analytics-engineer）、经济系统的叙事合理性（writer）
- **门禁 ID**：无；向 game-designer 汇报；变现决策需 creative-director 批准

---

## 静态断言（结构性）

- [ ] `description:` 字段存在且领域明确（提及经济、战利品表、成长曲线、平衡）
- [ ] `tools:` 为 `Read, Glob, Grep, Write, Edit`，`disallowedTools:` 为 `Bash` —— 仅限设计文档，不含代码或分析工具
- [ ] 模型层级为 `inherit` —— frontmatter 的 `model:` 严格为 `inherit`（层级见 `.claude/docs/model-tiers.md`）
- [ ] Agent 定义未声称对运营活动排期、代码或叙事拥有权限

## 测试用例

### 用例 1：域内请求 —— 宝箱战利品表设计
**输入**："为我们的地牢游戏设计一个标准宝箱的战利品表。"
**预期行为**：
- 起草前先提出澄清问题，并给出 2-4 个选项及推荐（问题优先工作流）—— 例如层级命名、宝箱是否使用保底计时或防脸黑保护
- 编写前读取 `design/registry/entities.yaml`，以已注册物品数值为准；与注册条目不符的数值标记为提议的注册表变更，不得静默使用
- 按奖励输出格式（产出、概率或权重、条件、备注）产出表格，含明确的稀有度层级 —— 普通、罕见、稀有、史诗、传说，或项目等效层级 —— 而非单一扁平物品列表
- 各层级概率构成完整分布：百分比合计 100%，或给出权重及其总和
- 说明各层级的预期获取量（平均需尝试几次获得），并指出表格背后的奖励节奏原则（奖励心理学）
- 主动提议注册新的跨系统物品："我可以将它们加入 `design/registry/entities.yaml` 吗？"

### 用例 2：域外请求 —— 季节性活动排期
**输入**："设计我们夏季活动和秋季活动的排期。何时运行、各持续多久？"
**预期行为**：
- 不产出活动排期或内容节奏计划
- 明确说明："运营活动排期由 live-ops-designer 负责；活动排期确定后，我负责设计活动内奖励的经济结构"
- 提议在 live-ops-designer 确定结构后，产出活动的奖励数值设计

### 用例 3：领域边界 —— 新货币的通胀风险
**输入**："我们要新增一种'声望币'货币，通过完成全部季节性内容获得。玩家可在声望商店消费。"
**预期行为**：
- 识别通胀风险：若声望币积累速度快于商店提供的消耗，商店将失去感知价值，玩家囤币不花
- 指出具体风险：季节性内容完成是有限的产出源，但若商店目录在赛季结束前被买空，赛季后期的币将无价值
- 提出消耗机制：轮换限时商店物品、声望商店中的消耗品，或货币兑换选项，以保持币持续消耗
- 未解决消耗问题前，不认可该设计在经济上合理
- 产出结构化风险评估：产出速率（估算每周币量）、消耗容量（估算买空目录所需币量）、盈余预测

### 用例 4：中期成长曲线问题
**输入**："玩家反馈中期 XP 刷取（20-35 级）像撞墙。每级需要 3 倍 XP，但奖励未按比例增长。"
**预期行为**：
- 识别为成长曲线问题：XP 成本增长率超过奖励增长率
- 产出修订的 XP 公式或曲线调整：降低 20-35 级的 XP 成本乘数、提高该区间的奖励 XP，或引入追赶机制（完成显著低于玩家等级的内容给予额外 XP）
- 以含定义变量的公式陈述当前与提议曲线，并在 20–35 区间两端均含（如 20、25、30、35 级）评估两者 —— `coding-standards.md` 要求设计数学"以变量定义"，平衡数值须关联其来源公式
- 指出任何曲线变更都会影响满级时间预测 —— 说明对终局内容节奏的下游影响（其成长曲线设计模型预测各阶段玩家预期战力）

### 用例 5：上下文传递 —— 基于当前经济数据的平衡分析
**输入上下文**：当前经济数据：玩家平均每小时赚 450 金币，商店物品平均 2,000 金币，平均单次游戏时长 40 分钟。高级物品 5,000 金币。
**输入**："我们当前的金币经济健康吗？应调整价格还是赚取速率？"
**预期行为**：
- 使用提供的具体数字：450 金币/小时 = 每 40 分钟 300 金币；2,000 金币物品需约 4.4 小时（约 6.7 次游戏）才能买得起；5,000 金币高级物品需约 11.1 小时（约 16.7 次游戏）
- 将这些获取时间对照其经济健康指标（每小时平均货币、物品获取速率）评估
- 给出锚定数字的选项 —— 如提高赚取速率或降低高级物品价格 —— 附各选项对应的小时数与游戏次数，给出推荐，并将选择权留给用户（问题优先工作流）
- 不产出未锚定所提供数据的泛泛建议（"价格可能过高"）

## 协议合规

- [ ] 保持在声明的领域内（战利品表、成长曲线、资源经济、通胀/通缩分析）
- [ ] 将运营活动排期请求转交 live-ops-designer，不产出排期
- [ ] 主动标记通胀/通缩风险，附量化的消耗/产出分析
- [ ] 以含定义变量和具体数字的公式陈述成长曲线变更 —— 不做模糊的曲线调整
- [ ] 使用上下文中的实际经济数据；有具体数据时不产出通用基准
- [ ] 编写物品前检查 `design/registry/entities.yaml`，标记对已注册数值的任何变更
- [ ] 创建多章节文档前询问"我可以创建 [filepath] 及章节骨架吗？"，写入每个章节前询问"我可以将此章节写入 [filepath] 吗？"

## 覆盖说明
- 用例 1 考察注册表意识 —— 在测试夹具中包含 `design/registry/entities.yaml`
- 用例 3（通胀风险）是经济健康测试 —— 遗漏通胀风险会对在线游戏经济造成长期损害
- 用例 4 要求 Agent 产出实际数字而非曲线形状 —— 验证数学存在，而非仅叙述
- 用例 5 是最重要的上下文意识测试；Agent 必须使用提供的数据，而非占位值
- 无自动化运行器；手动审查或通过 `/skill-test`
