# Agent 测试规范：release-manager

## Agent 摘要
- **领域**：发布流水线（构建 → 测试 → 认证 → 提交 → 验证 → 上线）、按 `platform.cert_tier` 划分的平台认证清单、商店提交与商店页面管理、年龄分级、语义化版本号与发布标签、发布日协调、发布后监控
- **不负责**：游戏设计、功能与范围决策（producer）、QA 测试策略与测试用例设计（qa-lead）、构建流水线与 CI/CD（devops-engineer）、营销文案（community-manager）
- **Gate ID**：无；由 `/team-release` 为发布候选版本和 Go/No-Go 签核生成。其阻塞性输出是预加载的 `/release-checklist` 给出的 `NOT READY` Go/No-Go 结论，上报给 producer

---

## 静态断言（结构性）

- [ ] `description:` 字段存在且领域明确（提及发布流水线、认证、商店提交）
- [ ] `tools:` 为 `Read, Glob, Grep, Write, Edit, Bash` — Bash 用于发布打标签（"每个发布点都必须将版本标签应用到 git 仓库"）
- [ ] `skills:` 预加载 `release-checklist`、`changelog` 和 `patch-notes`
- [ ] 模型层级为 `inherit` — frontmatter 的 `model:` 精确为 `inherit`（层级说明：`.claude/docs/model-tiers.md`）
- [ ] Agent 定义不声称对 QA 策略、游戏设计或构建基础设施拥有权限
- [ ] 其下一步建议自行运行 `/patch-notes [version]`，并将结果交给 community-manager 发布公告 — 绝不给 community-manager 一份让其撰写补丁说明的简报
- [ ] 流水线的测试步骤采用发布门禁的层级：`workflow: full` 时需 QA 签核（`standard` 时建议），任何层级都不得有未关闭的 S1，`full` 时也不得有未关闭的 S2 或 S3

## 测试用例

### 用例 1：领域内请求 — 主机提交的认证清单
**输入上下文**：`project.yaml` 设置 `platform.cert_tier: console`；游戏在 Nintendo Switch 上发行。
**输入**："为我们的 Nintendo Switch 提交生成认证清单。"
**预期行为**：
- 输出其预加载的 `/release-checklist` 为 `cert_tier: console` 定义的主机认证区块 — TRC/TCR/Lotcheck 要求清单、第一方提交、成就/奖杯集成、家长控制、存档数据规则（损坏、存储已满、用户切换）、年龄分级 — 外加主机设备要求（手柄提示、挂起/恢复、用户切换、连接中断、存储已满）
- 逐项跟踪每项要求，标注通过 / 失败 / 不适用状态（平台认证要求）
- 不输出 itch.io 或 Steamworks 认证行 — 认证区块遵循 `cert_tier`，而非请求中指定的平台
- 以 `/release-checklist` 的三个词给出 Go / No-Go 结论（READY / NOT ASSESSED / NOT READY，先匹配者胜）— 此处为 NOT ASSESSED 或 NOT READY，绝不为 READY，因为测试夹具未提供构建或测试证据 — 并在写入前询问"我可以将其写入 `production/releases/release-checklist-[version].md` 吗？"

### 用例 2：领域外请求 — 设计测试用例
**输入**："为我们的存档系统编写测试用例，确保它能通过认证。"
**预期行为**：
- 不产出测试用例规范
- 将测试设计转交 `qa-lead`，其委派映射中指定 qa-lead 负责质量门禁、测试结果和发布就绪签核
- 提供其自身负责的内容：测试必须覆盖的存档数据认证要求（主机区块的"存档数据规则合规（损坏、存储已满、用户切换）"），作为 qa-lead 的输入

### 用例 3：领域边界 — 年龄分级被拒阻塞发布
**输入**："我们的构建被 ESRB 拒绝。拒绝理由指出内容未反映在我们的分级提交中：调试输出中出现了一个隐藏的脏话字符串，并出现在了截图中。"
**预期行为**：
- 将拒绝视为阻塞：流水线在失败步骤处暂停，直到问题解决（"任何步骤都不得跳过。若某步骤失败，流水线暂停，问题解决后再继续"）
- 返回 Go / No-Go 结论为 NOT READY，将分级问题列为阻塞项并给出预计解决时间（`/release-checklist` 的 Go / No-Go 理由）
- 确定所需操作：移除所有包含该内容的调试输出，然后重新提交分级问卷并跟踪新证书的接收（商店页面管理：年龄分级）
- 不淡化问题，也不提议绕过问题上线 — 分级被拒是阻塞事件，而非建议性事项
- 向 producer 报告延迟对发布日的影响，其向 producer 汇报以进行排期

### 用例 4：版本号冲突 — 热修复 vs. 发布分支
**输入**："我们的发布分支在 v1.2.0。一个热修复直接应用在 main 上并打了 v1.2.1 标签。现在发布分支也有需要作为 v1.2.1 发布的变更，但它们是不同的变更。"
**预期行为**：
- 识别冲突：两个不同的变更集被分配了同一版本号
- 用语义化版本解决：`v1.2.1` 保留给已打标签的构建，发布分支的变更属于修复，作为下一个 PATCH（`v1.2.2`）发布 — 其版本号规则针对两个变更集争用一个版本号的情况
- 不接受一个版本号命名两个不同构建的状态 — "已应用的标签绝不移动或复用"，内部构建通过 `MAJOR.MINOR.PATCH.BUILD` 保持可区分
- 与 `lead-programmer` 协调热修复分支一侧，其委派映射中指定 lead-programmer 负责热修复分支管理

### 用例 5：上下文传递 — 发布日期约束与认证前置时间
**输入上下文**：目标发布日期为 2026-06-01。当前日期为 2026-04-06。Nintendo Lotcheck 通常需要 4-6 周。
**输入**："鉴于我们的时间线，认证清单上应优先处理什么？"
**预期行为**：
- 基于提供的日期和前置时间计算，而非占位估算：距发布 8 周，因此首次 Lotcheck 提交截止于 2026-04-20（若需 6 周）至 2026-05-04（若需 4 周）之间 — 在任何重新提交之前
- 保持流水线顺序和每个步骤 — 构建 → 测试 → 认证 → 提交 → 验证 → 上线，"任何步骤都不得跳过" — 并从发布日期倒排，而非压缩或删减步骤来凑时间
- 至少规划一次认证迭代（认证即"提交平台认证、跟踪反馈、迭代"），并指出一次拒绝就会耗尽剩余缓冲
- 给出建议顺序，但将排期决定交给 `producer` — 其向 producer 汇报以进行排期和优先级排序，削减范围是 producer 的职责（"决定包含或排除哪些功能（上报给 producer）"）

## 协议合规

- [ ] 保持在声明的领域内（发布流水线、认证清单、版本号、商店提交）
- [ ] 将测试用例设计请求转交 qa-lead，不产出测试规范
- [ ] 认证或分级失败时返回 NOT READY 并暂停流水线 — 不降级为建议性事项
- [ ] 应用语义化版本，绝不让一个版本号命名两个构建
- [ ] 认证范围遵循 `platform.cert_tier`，基于提供的日期排期且不跳过流水线步骤

## 覆盖说明
- 用例 3（分级被拒时返回 NOT READY）是最关键的测试 — 此 Agent 的主要安全输出是阻塞不良发布
- 用例 1 假设 `platform.cert_tier: console`；若该键未设置，预期输出是询问哪些平台在范围内，或 `NOT ASSESSED — cert tier unknown`，绝不为所有认证轨道
- 用例 5 需要当前日期和发布日期上下文；验证 Agent 使用实际日期，而非占位估算
- 认证要求随时间变化 — 若 Agent 产出可能过时的具体要求 ID，需标记
- 无自动化运行器；手动审查或通过 `/skill-test` 审查
