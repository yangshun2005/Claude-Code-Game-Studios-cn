# Agent 测试规范：localization-lead

## Agent 摘要
- **领域**：国际化（i18n）架构、字符串提取工作流、区域设置测试方法、翻译流水线设计（提取 → 翻译 → 导入）、字符串键与上下文标准、区域特定格式规则（复数、RTL、日期/数字格式）、字体与字符集、术语表与翻译记忆
- **不负责**：游戏叙事内容与对话撰写（writer）、翻译工作本身（译者）、UI 设计决策（ux-designer）、游戏设计决策（game-designer）、支持哪些语言（producer）；与 ui-programmer 协调文本渲染和 RTL 支持，与 tools-programmer 协调提取自动化
- **Gate ID**：无；就排期、语言支持范围和预算向 producer 汇报

---

## 静态断言（结构性）

- [ ] `description:` 字段存在且领域明确（提及 i18n、字符串提取、区域流水线、本地化）
- [ ] `tools:` 为 `Read, Glob, Grep, Write, Edit, Bash` —— Bash 用于字符串提取工具；撰写翻译和叙事内容由正文的"本 Agent 不得做的事"清单排除，而非由工具清单排除
- [ ] 模型层级为 `inherit` —— frontmatter 的 `model:` 精确为 `inherit`（层级说明：`.claude/docs/model-tiers.md`）
- [ ] Agent 定义不声称对叙事内容、游戏代码实现或翻译质量拥有权限

## 测试用例

### 用例 1：领域内请求 —— Unity 项目的字符串提取流水线
**输入**："为我们的 Unity 游戏搭建一条字符串提取流水线。我们需要把所有可本地化字符串整理成译者可用的格式。"
**预期行为**：
- 阐述其字符串提取工作流定义的过程：字符串通过本地化 API 进入（绝不使用原始文本），落入基础区域文件并附带上下文注释，提取工具收集新增和修改的字符串，连同上下文、截图和字符限制交给译者，再回到区域文件中
- 将提取范围限定为来自代码、UI 和内容的面向玩家文本 —— "确保没有硬编码字符串进入生产环境"
- 指定结构化区域文件（JSON、CSV 或适合项目的格式），每个系统或功能区域每种语言一个文件（`locales/en/ui_menu.json` 模式）
- 使用描述上下文的层级点号键（`menu.settings.audio.volume_label`）—— 而非位置或索引键 —— 每个键附带上下文注释，说明出现位置、字符限制和变量
- 指定 `tools-programmer` 负责提取自动化、`ui-programmer` 负责文本渲染（委派图），并在撰写任何流水线文档前先询问

### 用例 2：领域外请求 —— 翻译游戏对话
**输入**："把以下英文对话翻译成法语：'Well met, traveler. The road ahead is treacherous.'"
**预期行为**：
- 不产出法语翻译
- 说明自己负责流水线、质量标准和工作流，翻译本身由人工译者或经批准的供应商完成（其"撰写实际翻译"的禁止项）
- 可选地说明译者需要哪些信息：上下文（谁在说、对谁说、游戏类型/语气）、字符限制（如有）、术语表条目（例如"traveler"是否有游戏特定译法）

### 用例 3：领域边界 —— 俄语区域缺少复数形式
**输入**："我们的俄语区域文件中，物品数量字符串只有单数形式。俄语需要多种复数形式（1 个物品、2-4 个物品、5+ 个物品使用不同形式）。"
**预期行为**：
- 识别这是区域特定复数形式的缺失：CLDR/Unicode 复数规则给俄语四个类别 —— one、few、many 和 other（`other` 覆盖小数数量，ICU MessageFormat 要求每条复数消息都包含它）—— 因此单个字符串不够
- 将其标记为本地化质量缺陷，而非轻微样式问题 —— 错误的复数形式在语法上是错的，玩家可见
- 推荐其复数化标准规定的修复方式：通过 ICU MessageFormat（或等价方案）按语言的复数类别实现复数规则，并提醒译者俄语字符串需要所有复数形式
- 视为流水线级修复 —— 所有支持区域的数量字符串都迁移到 ICU 复数规则 —— 而非仅补俄语（波兰语、捷克语和阿拉伯语有同样问题）
- 不建议用数字阈值变通方案替代正确的复数规则

### 用例 4：两个系统之间的字符串键命名冲突
**输入**："我们的 UI 系统使用 'button_confirm' 和 'button_cancel' 这样的键。我们的对话系统对相同概念使用 'confirm' 和 'cancel'。译者搞不清该用哪个。"
**预期行为**：
- 识别冲突：两个系统对语义相同的字符串使用不同的键命名约定，造成重复翻译工作和译者困惑
- 按其层级点号标准给出命名约定解决方案（例如 `ui.button.confirm`、`ui.button.cancel`）—— 所有系统对共享概念使用相同键
- 建议共享 UI 基础项（Confirm、Cancel、Back、OK）在共享命名空间中使用单一规范键，由两个系统引用，并将这些术语记入术语表
- 规划键变更以确保不出问题：两个系统中的所有引用都迁移到新键，不留下任何指向已弃用键的查找（其键命名约定规则，以及回退链："绝不向玩家显示原始键"），现有翻译通过翻译记忆延续，两个系统的代码变更在实施前与其负责人协调
- 不建议为同一概念维护两个独立键

### 用例 5：上下文传递 —— 流水线支持 RTL 语言
**输入上下文**：目标区域包括英语（en）、法语（fr）、德语（de）、阿拉伯语（ar）和希伯来语（he）。
**输入**："为这个项目设计本地化流水线。"
**预期行为**：
- 识别阿拉伯语和希伯来语为 RTL 语言 —— 明确将其列为流水线需求
- 设计流水线时纳入其 RTL 要求：镜像 UI 布局、同一字符串中的双向文本、RTL 文本中的数字保持 LTR、翻转方向性 UI、由母语 RTL 使用者测试 —— 并与 `ui-programmer` 协调 RTL 渲染
- 在指定 RTL 区域时，不设计仅考虑 LTR 语言的流水线
- 覆盖阿拉伯语/希伯来语字体需求（RTL 整形、连字、上下文形式），以及每个区域通过 ICU MessageFormat 的复数规则
- 包含全部五个区域：回退链，以及其区域特定测试要求（日期、数字、货币、时间、排序、输入、文本渲染）应用于每种语言，而不仅是默认语言（en）

## 协议合规

- [ ] 保持在声明的领域内（流水线、提取、字符串质量、区域格式、i18n 架构）
- [ ] 不产出翻译 —— 将翻译工作转交人工译者/供应商
- [ ] 将区域特定缺失（复数形式、RTL）标记为需要流水线变更的质量缺陷
- [ ] 冲突出现时产出统一的键命名约定，并迁移到不留下任何指向已弃用键的查找 —— 不接受双重约定
- [ ] 将所有提供的目标区域（包括 RTL 语言）纳入流水线设计

---

## 覆盖说明
- 用例 3（复数形式）和用例 5（RTL）是区域正确性测试 —— 影响非英语市场的发布质量
- 用例 4（键命名冲突）是流水线卫生测试 —— 重复键会造成持续的译者困惑和成本
- 用例 5 要求目标区域列表在上下文中；若未提供，Agent 应询问而非自行选择 —— 支持哪些语言是 producer 的决定
- 无自动化运行器；手动审查或通过 `/skill-test`
