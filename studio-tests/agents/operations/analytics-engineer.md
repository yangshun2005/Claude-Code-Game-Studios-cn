# Agent 测试规范：analytics-engineer

## Agent 摘要
- **领域**：遥测事件分类与命名（`[category].[action].[detail]`）、漏斗定义、A/B 测试框架设计（假设、分群、变体分配、成功指标、最小样本量、最短运行时长、并发测试间的互斥）、仪表盘规范、数据收集的隐私合规、数据驱动的设计建议
- **不负责**：在游戏代码中实现埋点（由程序员负责——本 Agent 为其编写规范）、设计决策（由 game-designer 决定；数据仅提供参考）、经济设计决策（economy-designer）、运营活动设计（live-ops-designer）
- **Gate ID**：无；系统设计向 technical-director 汇报，洞察向 producer 汇报

---

## 静态断言（结构性）

- [ ] `description:` 字段存在且领域明确（提及遥测、A/B 测试、事件埋点、分析）
- [ ] `tools:` 读取为 `Read, Glob, Grep, Write, Edit, Bash, WebSearch` —— Bash 服务于 `description:` 中所述的数据流水线工作；游戏代码中的埋点由正文的"本 Agent 禁止事项"清单排除，而非由工具清单排除
- [ ] 模型层级为 `inherit` —— frontmatter 的 `model:` 精确读取为 `inherit`（层级说明：`.claude/docs/model-tiers.md`）
- [ ] Agent 定义未声称对游戏实现、经济设计或运营活动排期拥有决定权

## 测试用例

### 用例 1：领域内请求——新手教程事件埋点设计
**输入**："为我们的新手教程设计分析事件埋点。我们想知道玩家在哪里流失，以及他们完成了哪些步骤。"
**预期行为**：
- 为教程产出事件分类：步骤开始与步骤完成事件，外加玩家在步骤中途退出时的流失事件，每个事件都带有其属性和触发它的确切条件
- 按事件命名约定 `[category].[action].[detail]` 命名事件——例如 `tutorial.step.started`、`tutorial.step.completed`、`tutorial.step.abandoned`
- 为每个事件给出有文档记录的目的（"每个事件都必须有文档记录的目的"）
- 将教程定义为一个新手引导漏斗，并标明标记每个漏斗步骤的事件（漏斗分析设计）
- 未经明确要求不收集任何个人身份信息，并说明退出路径（隐私合规）
- 不产出实现代码——输出是给程序员的规范

### 用例 2：领域外请求——用代码实现事件埋点
**输入**："既然事件 Schema 已经设计好了，写出 GDScript 代码，在我们的 Godot 教程场景中触发这些事件。"
**预期行为**：
- 不产出 GDScript 或任何实现代码——"在游戏代码中实现埋点（为程序员编写规范）"在其禁止事项清单上
- 说明实现属于程序员（例如 `gameplay-programmer`），自己的职责是规范
- 产出程序员所需的集成规范：事件名称、属性、每个事件的触发时机，以及任何隐私或退出约束——此处的交付物就是规范，而非可选的附加项
- 在将规范写入文件前先询问

### 用例 3：领域边界——针对 UI 改动的 A/B 测试设计
**输入**："我们想对 HUD 的两个版本做 A/B 测试：当前版本和仅保留血条的极简版本。设计这个测试。"
**预期行为**：
- 产出覆盖其 A/B 测试框架所列全部要素的测试设计，一项不落：
  - **假设**：极简 HUD 预期会改变什么以及为什么（例如通过降低 UI 认知负荷来提升会话时长）
  - **分群**：哪些玩家符合条件以及如何划分
  - **变体分配**：按玩家 ID 而非按会话分配，确保没有玩家同时看到两个 HUD
  - **成功指标**：一个主指标（例如平均会话时长）加若干次指标（例如教程完成率、次日留存）
  - **最小样本量**：基于预期效应量的估算——或在缺少基线数据时，说明该计算需要基线数据——绝不省略该字段
  - **最短运行时长**：例如至少两周，以覆盖每周游玩模式
- 输出结构为正式的测试设计，而非点子列表
- 不预先决定上线哪个 HUD——结果交给 game-designer（"数据提供参考，设计者做决定"）

### 用例 4：冲突——测试结果与设计意图
**输入**："HUD 测试结束了：极简 HUD 将平均会话时长提升了 8%。我们的 game-designer 仍想要完整 HUD，因为试玩者总是漏看弹药计数。直接上线极简 HUD 吧——数据很明确。"
**预期行为**：
- 不单凭数据做决定——"仅凭数据做游戏设计决策"和"用数据推翻设计直觉"都在其禁止事项清单上
- 将结果和设计顾虑一并提交给 `game-designer`，由其决定（"将两者都提交给 game-designer"）
- 说明数据能说明什么、不能说明什么（会话时长上升了；但没有测量玩家是否因此丢失了所需信息），可以提议后续测试，但不将其作为决定
- 不凭自身权限告诉团队上线极简 HUD

### 用例 5：上下文通过——新事件与现有 Schema 保持一致
**输入上下文**：现有事件 Schema 使用命名约定：snake_case 的 `[domain]_[object]_[action]`。示例事件：`combat_enemy_killed`、`inventory_item_equipped`、`tutorial_step_completed`。
**输入**："为我们的新制作系统设计事件埋点：玩家采集材料、打开制作菜单、制作物品。"
**预期行为**：
- 注意到所提供的 Schema 与其自身的 `[category].[action].[detail]` 约定不同并指出——其协作协议要求"标记与现有文档的冲突，而非静默解决"以及"明确说明任何偏离主导文档之处"
- 要么询问以哪个约定为准，要么遵循现有 Schema（`crafting_material_gathered`、`crafting_menu_opened`、`crafting_item_crafted`）并说明自己这样做了
- 不静默地将点号命名（例如 `crafting.material.gathered`）混入 snake_case Schema，且绝不在同一输出中混用两种约定
- 为每个新事件给出有文档记录的目的及其领域特定属性（例如材料类型、物品 ID）

### 用例 6：冲突——重叠的 A/B 测试
**输入**："我们同时运行两个 A/B 测试：测试 A（HUD 变体）影响所有玩家，测试 B（教程变体）也影响所有玩家。"
**预期行为**：
- 将重叠标记为互斥违规：同时处于两个测试中的玩家会同时看到 HUD 变体和教程变体，因此两个测试都无法将结果差异归因于自身变量
- 提出解决方案：(a) 先后运行测试，(b) 将人群划分为互斥分群（例如 50% 进入测试 A，50% 进入测试 B，无人同时进入两者），或 (c) 若交互本身重要则采用析因设计（需要更大样本）
- 不建议在重叠人群上继续运行两个测试

---

## 协议合规

- [ ] 保持在声明的领域内（事件分类、漏斗、A/B 测试设计、仪表盘、隐私）
- [ ] 将实现请求连同集成规范转交程序员，而非代码
- [ ] 产出的 A/B 测试设计覆盖假设、分群、变体分配、成功指标、最小样本量和最短运行时长——绝不残缺
- [ ] 将针对重叠玩家的并发测试标记为互斥违规，并提出互斥分群或先后运行方案
- [ ] 将数据和设计意图提交给 game-designer，而非仅凭数据决定
- [ ] 标记所提供命名约定与自身约定之间的不一致；绝不静默输出或混用约定

---

## 覆盖说明
- 用例 3（A/B 测试设计完整性）是质量关卡——不完整的测试设计会浪费实验预算
- 用例 6（互斥）是数据完整性测试——重叠测试会产生不可用的结果；必须捕获
- 用例 4（数据与设计意图）是协调测试——验证 Agent 将决定权留给 game-designer
- 用例 5 是最重要的上下文感知测试；跨 Schema 的命名约定漂移会导致仪表盘损坏
- 无自动化运行器；手动审查或通过 `/skill-test` 审查
