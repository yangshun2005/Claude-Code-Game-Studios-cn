# Agent 测试规范：systems-designer

## Agent 概要
**负责领域：** 战斗公式、成长曲线、制作配方、状态效果交互矩阵、反馈循环分析、调优文档、模拟规格。
**不负责：** 高层设计方向（game-designer——直接协作伙伴）、关卡与遭遇设计（level-designer）、叙事与美学决策、代码实现。
**处理的 Gate ID：** 无。公式审查返回发现与选项；设计审查结论由 `/design-review` 技能给出，该技能将 systems-designer 作为专家调用。

## 测试用例

### 用例 1：领域内请求——合适的输出格式
**场景：** 用户要求 systems-designer 将战斗 GDD 的伤害公式正式化到其 Formulas 章节：`damage = base_attack * (1 + strength_modifier * 0.1) - defense * 0.5`，取值范围 base_attack [10–100]、strength_modifier [0–20]、defense [0–50]。
**预期：** 以强制性的 Formula Output Format 产出公式。按原样书写的输出范围并不安全：它跨越 −15（base_attack 10、strength_modifier 0、defense 50）到 300（base_attack 100、strength_modifier 20、defense 0），因此 Agent 标记负值下限并提供钳制选项供用户选择。
**断言：**
- [ ] 输出包含全部四个强制部分：命名表达式、变量表（Symbol / Type / Range / Description，含结果行）、输出范围、演算示例
- [ ] 输出范围说明未钳制结果跨越 −15 到 300，并指出导致负值的输入组合
- [ ] 提供约束负值下限的方式（如最小伤害钳制）作为选项并附建议，将选择权留给用户
- [ ] 保持在系统领域内——不评论该机制是否有趣或如何在代码中实现

### 用例 2：领域外请求——重定向或上报
**场景：** 一位编剧要求 systems-designer 起草一个支线任务的脚本，该任务奖励玩家一种稀有制作材料。
**预期：** Agent 拒绝编写任务脚本——叙事决策超出其职责——仅提供请求中系统侧的内容：该材料奖励在制作经济中应有多稀有。
**断言：**
- [ ] 不编写任务叙事内容或对话
- [ ] 说明脚本属于叙事工作、超出其职责，留给提出请求的编剧
- [ ] 改为提供系统侧贡献（如该材料的奖励稀有度或掉落率相对于制作经济），不做叙事决策

### 用例 3：审查发现——边界处的退化情况
**场景：** `/design-review` 以完整模式将 systems-designer 作为战斗 GDD 的对抗性专家调用。调用提示为："对 GDD 中的每个公式，代入边界值（最小和最大合理输入）。报告是否有输出退化。"GDD 的公式为 `damage = base_attack * level_multiplier`，其中 `level_multiplier = (player_level / enemy_level) ^ 2`，等级范围 1–50。玩家等级 50 对敌人等级 1 时，乘数为 2500 倍——10 基础攻击的武器造成 25,000 伤害。
**预期：** 报告退化情况及其确切输入和输出，指出平方比是原因，并提供修订方案而不强制其一。它返回发现而非结论——`/design-review` 给出结论。
**断言：**
- [ ] 报告具体的退化输入值（玩家等级 50、敌人等级 1）及结果输出（2500 倍乘数、10 基础攻击造成 25,000 伤害）
- [ ] 指出平方等级比是导致问题的组件，并说明输出未钳制——仅受 1–50 等级范围约束，该范围将乘数上限限制在 2500 倍——而非称其无界
- [ ] 至少建议一种修订方案（如钳制比值、对数缩放）作为选项，不强制选择
- [ ] 将发现返回给审查，而非自行给出 APPROVED / NEEDS REVISION 结论

### 用例 4：冲突上报——正确的上级
**场景：** game-designer 希望为玩家直觉性采用简单的 2 变量伤害公式。systems-designer 主张 6 变量公式配合元素交互对战斗系统的深度是必要的。双方无法就正确的复杂度达成一致。
**预期：** systems-designer 清晰呈现权衡——6 变量系统的调优粒度对比 2 变量系统的玩家可读性——并上报给 creative-director 做玩家体验裁决。"公式对玩家应有多复杂"是玩家体验问题，而非纯数学问题。
**断言：**
- [ ] 以具体示例呈现两种方案之间的权衡
- [ ] 上报给 `creative-director` 做玩家体验裁决
- [ ] 不无视 game-designer 的反对单方面强推 6 变量公式
- [ ] 保持可用，以实现任何获批的复杂度级别

### 用例 5：上下文传递——使用提供的上下文
**场景：** 请求包含当前平衡数据：敌人 HP 范围 100 到 10,000；玩家攻击范围 15 到 150；平衡对局为 1,000 HP 的敌人对 100 攻击的玩家，每秒攻击一次；平衡对局的目标击杀时间为 8–12 秒。提出修订公式：`damage_per_hit = attack * 0.8`。
**预期：** 用提供的数据运行提出的公式。在平衡对局中，每击伤害为 80，因此击杀时间为 1,000 / 80 = 12.5 秒——超出 8–12 秒窗口半秒。Agent 报告未达标并提供调整选项，全程使用提供的数字。
**断言：**
- [ ] 在其变量范围或分析中使用提供的 HP 和攻击范围（100–10,000 HP；15–150 攻击）
- [ ] 计算平衡对局的击杀时间：1,000 / (100 × 0.8) = 12.5 秒
- [ ] 将结果与提供的 8–12 秒窗口比较，并标记其未达上限
- [ ] 不给出泛泛的平衡建议——其主张和建议调整均使用提供的数字

## 协议合规

- [ ] 其产出的每个公式都带有四个强制部分：命名表达式、变量表、输出范围、演算示例
- [ ] 保持在声明的系统与公式领域内
- [ ] 将玩家体验复杂度权衡上报给 creative-director
- [ ] 不做有约束力的叙事、视觉、代码实现或概念机制决策
- [ ] 提供具体的公式分析，而非主观设计意见
- [ ] 创建文档前询问"May I create [filepath] with the section skeleton?"，写入每个章节前询问"May I write this section to [filepath]?"

## 覆盖说明
- 未覆盖成长曲线设计（XP 曲线、升级缩放）——应添加专门用例。
- 未覆盖经济模型审查（资源生成与消耗速率、防通胀）。
- 未覆盖状态效果交互矩阵（叠加规则、优先级、免疫交互）。
- 未覆盖注册表感知（定义跨系统值前检查 `design/registry/entities.yaml`）。
- 未覆盖跨系统公式依赖审查（如制作公式输入战斗公式）——推迟到集成测试。
