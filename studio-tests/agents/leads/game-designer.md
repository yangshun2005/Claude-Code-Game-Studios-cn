# Agent 测试规范：game-designer

## Agent 摘要
**负责领域：** 核心循环设计、成长系统、战斗机制规则、经济设计、面向玩家的规则与交互、`design/gdd/` 中的机制 GDD。
**不负责：** 代码实现（lead-programmer / gameplay-programmer）、美术与音频方向（art-director / audio-director）、最终叙事内容（narrative-director — 需协调）、详细公式数学（systems-designer — 委派给其处理）。
**处理的 Gate ID：** 无。设计评审结论来自 `/design-review` 技能（APPROVED / NEEDS REVISION / MAJOR REVISION NEEDED / NOT ASSESSED）；当该技能将 game-designer 作为专家启动时，Agent 返回发现项。

---

## 静态断言（结构性）

通过读取 Agent 的 `.claude/agents/game-designer.md` frontmatter 验证：

- [ ] `description:` 字段存在且领域特定（引用核心循环、成长、战斗规则、经济、面向玩家的设计 — 而非泛泛而谈）
- [ ] `tools:` 读取 Read、Glob、Grep、Write、Edit、WebSearch，且 `disallowedTools:` 列出 Bash
- [ ] 模型层级为 `inherit` — frontmatter `model:` 精确读取为 `inherit`（层级：`.claude/docs/model-tiers.md`）
- [ ] Agent 定义不声称对代码实现、视觉美术风格或独立叙事设定决策拥有权限

## 测试用例

### 用例 1：领域内请求 — 适当的输出格式
**场景：** 项目的 `modes.workflow` 为 `full`。用户要求 game-designer 设计一个"基于耐力的闪避"机制：玩家拥有耐力池，每次闪避消耗耐力，不闪避时耐力恢复，闪避提供短暂的无敌窗口。
**预期：** 遵循其 Question-First 工作流 — 询问闪避应让玩家产生什么感受以及如何与支柱关联，提出 2–4 个选项并给出推荐，然后按设计文档标准起草 GDD，将可调值暴露为调参旋钮，每次写入前询问。
**断言：**
- [ ] 在提出设计前询问澄清问题（预期玩家体验、支柱关联），并提出 2–4 个选项及推荐，将选择权留给用户
- [ ] 草稿使用设计文档标准的八个章节：概述、玩家幻想、详细规则、公式、边界情况、依赖、调参旋钮、验收标准
- [ ] 调参旋钮将每个值（耐力池、闪避消耗、恢复速率、无敌持续时间）分类为手感、曲线或门槛，并将其放在外部数据文件中而非硬编码
- [ ] 在创建文件前询问"我可以创建 [filepath] 及章节骨架吗？"，在写入 `design/gdd/` 下每个章节前询问"我可以将此章节写入 [filepath] 吗？"；不提供实现代码或美术方向

### 用例 2：领域外请求 — 重定向或上报
**场景：** 团队成员要求 game-designer 撰写世界观内关于耐力系统为何存在的叙事解释（例如，角色在游戏世界中拥有耐力上限的叙事原因）。
**预期：** Agent 拒绝撰写叙事/设定内容，并重定向至 writer 或 narrative-director。
**断言：**
- [ ] 不撰写叙事或设定内容
- [ ] 明确指定 `writer` 或 `narrative-director` 为正确处理者
- [ ] 其添加的任何设计意图（例如"耐力系统应强化物理真实感主题"）被框定为给叙事团队的输入，而非作为设定本身撰写

### 用例 3：评审发现项 — 具体，结论留给评审技能
**场景：** `/design-review` 在 full 模式下将 game-designer 作为 `design/gdd/environmental-hazards.md` 的对抗性专家启动。启动提示为："你的工作不是验证此设计 — 你的工作是发现问题。将你的评审锚定到 B 节中声明的玩家幻想。"玩家幻想为"世界危险但公平 — 每种危险都可读且可避免。"GDD 定义了三种危险类型（火、酸、电），但未指定玩家同时处于多种危险中时会发生什么、危险在闪避无敌窗口期间命中时会发生什么，或伤害频率（每秒、每 tick、进入时）。
**预期：** 返回具体发现项，指出三个未定义的边界情况，与声明的玩家幻想关联，作为待填补的空白而非对机制的拒绝。它返回发现项，而非结论 — `/design-review` 发布结论。
**断言：**
- [ ] 指出每个缺失的边界情况：同时多危险暴露、闪避无敌期间的危害、未定义的伤害频率
- [ ] 将至少一个空白与声明的玩家幻想关联（例如，未定义的伤害频率使危险的威胁不可读，与"可读且可避免"矛盾）
- [ ] 将空白框定为 GDD 中待定义的规则（应指定什么），而非对机制的拒绝，也非实现建议
- [ ] 将发现项返回给评审，而非自己的 APPROVED / NEEDS REVISION 印章

### 用例 4：冲突上报 — 正确的上级
**场景：** systems-designer 提出一个包含 6 个变量和复杂缩放交互的伤害公式，认为它能产生最佳的调参粒度。game-designer 认为该公式对玩家来说过于复杂难以直觉理解，想要一个更简单的 2 变量版本。
**预期：** game-designer 拥有概念规则和玩家体验意图（"伤害应对玩家来说感觉可理解"），但将公式粒度问题交由 systems-designer 决定。如果两者之间的分歧无法解决（一个想要复杂，一个想要简单），上报至 creative-director 进行玩家体验裁决。
**断言：**
- [ ] 清晰陈述玩家体验意图（直觉伤害、玩家自主权）
- [ ] 将公式粒度决策交由 `systems-designer`
- [ ] 将未解决的分歧上报至 `creative-director` 进行玩家体验仲裁裁决
- [ ] 不单方面将公式结构强加于 systems-designer

### 用例 5：上下文传递 — 使用提供的上下文
**场景：** 请求包含游戏的三条支柱："玩家自主性"、"后果永久性"和"世界响应性"。一份关于"带传承加成的永久死亡"的新机制规范提交给 Agent 评估。
**预期：** 评估针对所有三条提供的支柱评估该机制 — 永久死亡如何支持玩家自主性、传承加成如何表达或软化后果永久性、世界如何响应玩家死亡。直接使用支柱词汇，并标记支柱张力供用户决定。
**断言：**
- [ ] 在评估中按名称引用所有三条提供的支柱
- [ ] 明确评估该机制对每条支柱的贡献
- [ ] 不生成通用游戏设计建议 — 每个点都按名称与提供的支柱之一关联；框架术语（MDA、SDT）可支持某个点，但绝不替代其所涉及的支柱
- [ ] 标记至少一个具体的支柱张力（例如，传承加成软化"后果永久性"）作为用户决策的问题，而非其自行解决

### 用例 6：`modes.workflow: standard` 下的章节集
**场景：** 与用例 1 相同的"基于耐力的闪避"请求，但项目的 `modes.workflow` 为 `standard`。
**预期：** 起草 `standard` 要求的五个章节 — 概述、详细规则、边界情况、依赖、验收标准 — 加上公式，因为闪避定义了数值规则（耐力消耗、恢复速率、无敌持续时间）。
**断言：**
- [ ] 草稿包含概述、详细规则、边界情况、依赖和验收标准 — 依赖未被丢弃
- [ ] 包含公式，因为该机制定义了数值规则
- [ ] 在此层级不将玩家幻想或调参旋钮视为必需章节

## 协议合规性

- [ ] 按设计文档标准的章节起草机制文档，并在写入 `design/gdd/` 前逐章节询问
- [ ] 保持在声明的游戏设计领域内
- [ ] 未解决时将设计与公式冲突上报至 creative-director
- [ ] 不做出有约束力的代码实现、视觉美术或独立设定决策
- [ ] 提供可操作的设计反馈，而非实现处方

---

## 覆盖说明
- 经济设计评审（资源消耗、资源产出、防通胀）未覆盖 — 应添加专门用例。
- 成长系统评审（XP 曲线、解锁门槛、玩家能力轨迹）未覆盖。
- 直接的"评审此 GDD"请求未覆盖 — 设计评审结论来自 `/design-review`，由用户运行。
- `modes.workflow` 为 `minimal` 时的机制编写（无 GDD，`design/game-brief.md` 为设计记录）未覆盖。
- 跨多个互连系统的核心循环验证（不仅是单一机制）未覆盖 — 推迟至 /review-all-gdds 集成。
- 与 systems-designer 关于公式所有权边界的协调协议可受益于额外用例。
