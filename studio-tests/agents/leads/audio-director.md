# Agent 测试规范：audio-director

## Agent 摘要
**负责领域：** 声音身份——声音调色板、音乐方向与情感映射、音频事件架构、混音策略、自适应音频设计、音频资产规范与命名。
**不负责：** 视觉设计（art-director）、音频引擎代码（gameplay-programmer / engine-programmer）、音频中间件变更（需 technical-director 批准）、叙事故事内容（narrative-director）、UX 交互流程（ux-designer）。
**处理的 Gate ID：** 无。audio-director 未分配任何导演 Gate（`AD-` 系列 Gate 属于 art-director）。设计评审结论由 `/design-review` 技能产出，该技能将 audio-director 作为专家调用并返回发现。

## 静态断言（结构性）

通过阅读 Agent 的 `.claude/agents/audio-director.md` frontmatter 验证：

- [ ] `description:` 字段存在且领域明确（提及音乐方向、声音设计、混音、音频实现——而非泛泛描述）
- [ ] `tools:` 包含 Read、Glob、Grep、Write、Edit、WebSearch，且 `disallowedTools:` 列出 Bash
- [ ] 模型层级为 `inherit`——frontmatter `model:` 精确为 `inherit`（层级说明见 `.claude/docs/model-tiers.md`）
- [ ] Agent 定义未声称对视觉设计、代码实现或叙事内容拥有权限

## 测试用例

### 用例 1：领域内请求——输出格式恰当
**场景：** 用户已批准游戏"探索"音乐层的方向：一个生成式环境系统，由分层音轨组成，随环境密度变化，采用稀疏、有机、略带忧郁的调色板，旨在强化支柱"有人居住的世界"。用户要求 audio-director 为该层起草音频资产规范。
**预期：** 以 Agent 自有格式起草规范：每个资产按音频命名约定命名，每个类别给出格式、采样率、响度目标和文件大小预算，并将音轨/密度行为与支柱关联。展示草稿，并在写入文件前询问。
**断言：**
- [ ] 每个资产名遵循 `[category]_[context]_[name]_[variant].[ext]`（例如 `mus_explore_forest_calm_loop.ogg`）
- [ ] 为音乐资产指定格式、采样率、响度目标（LUFS）和文件大小预算
- [ ] 理由将密度驱动的音轨分层与"有人居住的世界"支柱关联
- [ ] 保持在音频范围内，并在创建文件前询问"May I create [filepath] with the section skeleton?"，在写入每个章节前询问"May I write this section to [filepath]?"

### 用例 2：领域外请求——重定向或上报
**场景：** 开发者要求 audio-director 评估音频设置菜单的 UI 流程（屏幕和选项的顺序）是否直观且组织良好。
**预期：** Agent 不对屏幕流程或菜单组织做裁定——那属于 UX，而非音频。它将回答限定为菜单必须暴露的音频需求，这些需求源自其自身的混音策略，并将流程和布局留给 ux-designer。
**断言：**
- [ ] 不对 UI 流程、屏幕顺序或信息架构做任何约束性决定
- [ ] 声明流程和布局超出音频领域，而非对其进行评估
- [ ] 明确指出 `ux-designer` 是菜单流程和布局的负责人（其文件将 UX 决策交由 ux-designer）
- [ ] 将其贡献限定为取自其混音策略的音频需求（例如，其音量层级中每条总线一个滑块——主音量、音乐、音效、对话）

### 用例 3：评审发现——具体，结论留给评审技能
**场景：** `/design-review` 以完整模式将 audio-director 作为对抗性专家调用，审查一份包含音乐触发器的 Boss 战 GDD。调用提示为："你的工作不是验证此设计——你的工作是找出问题。要具体、要批判。"GDD 的最终 Boss 提示音乐是一首欢快、大调、快节奏的管弦乐作品；该遭遇的游戏支柱和叙事背景指定为"恐惧、必然性和悲剧性牺牲"。
**预期：** 返回具体发现：提示音乐的大调、快节奏和欢快音区与情感目标矛盾，并以选项形式提供修改方向。它返回发现，而非结论——评审结论由 `/design-review` 产出。
**断言：**
- [ ] 识别出冲突的具体音乐特征（大调、快节奏、欢快音区）
- [ ] 指出提示音乐所矛盾的情感目标（恐惧、必然性、悲剧性牺牲），并将其视为该遭遇的情感映射
- [ ] 提供可操作的修改方向（例如小调、更慢的节奏、更薄的编制）作为选项并附建议
- [ ] 将发现返回给评审，而非自行给出 APPROVED / NEEDS REVISION 标记

### 用例 4：冲突上报——正确的上级
**场景：** sound-designer 提议使用基于实时射线检测的物理查询来实现音频遮挡。technical-artist 认为这太昂贵，提议改用基于区域的触发器系统。双方都同意遮挡效果是可取的；冲突纯粹在于实现方式。
**预期：** audio-director 定义期望的音频行为（遮挡听起来应如何、何时激活）作为任一方案都必须满足的需求，然后将射线检测 vs. 区域的选择交由 `lead-programmer`——其文件指定的音频系统实现负责人——或交由 `technical-director` 处理技术冲突。它不选择实现方式，也不将决定交给争议中的任何一方。
**断言：**
- [ ] 清晰定义期望的音频行为（玩家听到什么、遮挡何时生效、衰减强度如何）
- [ ] 将实现方式（射线检测 vs. 区域触发器）交由 `lead-programmer` 或 `technical-director`——而非争议方 sound-designer 或 technical-artist
- [ ] 不单方面选择技术实现方法
- [ ] 将音频行为表述为任一实现都必须满足的需求，以便据此检验技术决策

### 用例 5：上下文传递——使用提供的上下文
**场景：** 请求中包含游戏的三条支柱："涌现故事"、"有意义的牺牲"和"有人居住的世界"。提交了一份环境氛围音频规范：每个生物群系一个静态循环，没有任何层响应玩家行为或世界事件。
**预期：** 评估按名称对照全部三条支柱评估氛围规范。指出静态循环不支持"涌现故事"，因为音频中没有任何内容响应游戏状态，并指出自适应音频是缺口。
**断言：**
- [ ] 在评估中按名称引用全部三条提供的支柱
- [ ] 明确评估音频规范对每条支柱的贡献
- [ ] 指出"涌现故事"未得到支持，因为循环不响应游戏状态，并指出自适应音频（状态驱动的层或过渡）是缺失的部分
- [ ] 不生成泛泛的音频方向建议——所有反馈都与提供的支柱词汇关联

## 协议合规

- [ ] 为其指定的每个音频资产按 `[category]_[context]_[name]_[variant].[ext]` 命名
- [ ] 保持在声明的音频领域内
- [ ] 将实现方式决策交由技术负责人
- [ ] 将音频反馈与请求中提供的支柱或情感目标关联，而非泛泛的音频建议
- [ ] 不做约束性的视觉设计、UX、叙事或代码实现决定
