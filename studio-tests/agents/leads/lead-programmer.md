# Agent 测试规范：lead-programmer

## Agent 摘要
**负责领域：** 代码架构决策、LP-FEASIBILITY 门禁、LP-CODE-REVIEW 门禁、编码规范执行、已批准引擎内的技术栈决策。
**不负责：** 游戏设计决策（game-designer）、创意方向（creative-director）、制作排期（producer）、视觉艺术方向（art-director）。
**处理的门禁 ID：** LP-FEASIBILITY、LP-CODE-REVIEW。

---

## 静态断言（结构性）

通过读取该 Agent 的 `.claude/agents/lead-programmer.md` frontmatter 验证：

- [ ] `description:` 字段存在且针对领域（提及代码架构、可行性、代码审查、编码规范——而非泛泛而谈）
- [ ] `tools:` 包含用于源文件的 Read 和用于静态分析或测试运行的 Bash；Write/Edit 在正文中受门禁约束——每次写入都等待用户说"yes"，编排运行例外仅覆盖 `production/`、`docs/` 或 `tests/` 下的新构建产物
- [ ] 模型层级为 `sonnet`——frontmatter 的 `model:` 精确为 `sonnet`（层级说明：`.claude/docs/model-tiers.md`）
- [ ] Agent 定义未声称对游戏设计、创意方向或制作排期拥有权限

## 测试用例

### 用例 1：领域内请求——适当的输出格式
**场景：** 一份新的 `CombatSystem` 实现被提交代码审查，包含 LP-CODE-REVIEW 要求的全部输入：其实现文件、其故事的验收标准、相关 GDD 章节（战斗规则）及其管辖 ADR。该系统保持在 ADR 边界内，按原文实现 GDD 的战斗规则，对所有外部引用使用依赖注入，所有公共 API 都有文档注释，从数据文件加载调优值，并为所有公共方法包含单元测试。请求标记为 LP-CODE-REVIEW。
**预期：** 返回裁决 APPROVE，理由确认 ADR 边界匹配、对 GDD 规则的正确性、依赖注入使用、文档注释覆盖、数据驱动配置以及可测试的公共 API。
**断言：**
- [ ] 裁决恰好为 APPROVE / CONCERNS / REJECT 之一（LP-CODE-REVIEW 的裁决）
- [ ] 明确陈述裁决词 `APPROVE`——`/story-done` 依据门禁的裁决词分支，因此隐含在叙述中的裁决无法被处理
- [ ] 理由引用其编码规范执行清单和门禁提示中的具体标准（ADR 边界、GDD 规则、DI、文档注释、数据驱动值、可测试 API）
- [ ] 输出保持在代码质量范围内——不评论该机制是否有趣或是否符合创意愿景

### 用例 2：领域外请求——重定向或上报
**场景：** 团队成员要求 lead-programmer 审查并批准玩家跨等级伤害缩放的平衡公式，检查数值是否"感觉对"。
**预期：** Agent 拒绝评估设计平衡，并重定向到 game-designer，即其声明的设计问题联系人。
**断言：**
- [ ] 不对公式平衡或游戏手感做出任何有约束力的评估
- [ ] 明确指定 `game-designer` 为正确处理者（其"本 Agent 不得做什么"中设计问题的目标）；同时指定 `systems-designer` 为公式负责人也可以
- [ ] 对公式的任何评论都是关于实现的（例如最高等级时的整数溢出风险）；所有平衡评估都交由设计团队

### 用例 3：门禁裁决——正确词汇
**场景：** 被审查的架构文档（已通过其技术需求基线和 ADR 列表）指定敌人 AI 每帧对所有其他实体运行暴力最近邻搜索。预期敌人数为 2,000+，这是 O(n²)——每帧约 400 万次距离检查——而文档在 60fps 下的 AI 预算为 2 ms。请求标记为 LP-FEASIBILITY。
**预期：** 返回裁决 INFEASIBLE，具体引用 O(n²) 复杂度、实体数量阈值以及由此产生的每帧成本与 2 ms AI 预算的对比。
**断言：**
- [ ] 裁决恰好为 FEASIBLE / CONCERNS / INFEASIBLE 之一——而非自由文本
- [ ] 明确陈述裁决词 `INFEASIBLE`，而非叙述隐含的裁决
- [ ] 理由包含具体算法复杂度和实体数量数字
- [ ] 建议至少一种替代方案（例如空间哈希、KD-tree），但不强制选择

### 用例 4：冲突上报——正确的上级
**场景：** game-designer 想要一个机制，让每个 NPC 维护需求、日程和记忆的完整模拟（类似完整的生活模拟 AI）。lead-programmer 计算出在目标 NPC 数量下这将超出帧预算 3 倍。game-designer 坚持该机制是游戏愿景的核心。
**预期：** lead-programmer 用数字陈述具体的帧预算违规，提出替代方案（例如基于 LOD 的模拟、简化需求模型），但明确将"这值得付出成本还是应改变设计"的决定交由 creative-director 作为创意仲裁者。
**断言：**
- [ ] 陈述具体的帧预算违规（例如在 N 个实体下超出预算 3 倍）
- [ ] 提出至少一种技术上可行的替代方案
- [ ] 明确将设计优先级决定交由 `creative-director`
- [ ] 不单方面削减或修改机制设计

### 用例 5：上下文传递——使用提供的上下文
**场景：** Agent 收到架构文档（含其技术需求基线和 ADR 列表）的门禁上下文块，其中包含项目的帧预算：每帧总计 16.67ms，其中 4ms 分配给 AI 系统。文档采用新的 AI 行为系统，原型性能分析估计正常条件下每帧将消耗 7ms。请求标记为 LP-FEASIBILITY。
**预期：** 评估引用上下文中的具体帧预算分配（4ms AI 预算），识别 7ms 估计超出分配 3ms，并返回 CONCERNS 或 INFEASIBLE，引用这些具体数字。
**断言：**
- [ ] 引用所提供上下文中的具体帧预算数字（总计 16.67ms，AI 分配 4ms）
- [ ] 在比较中使用提交中的具体 7ms 估计
- [ ] 不给出泛泛的"这可能很慢"建议——引用具体数字
- [ ] 裁决理由可追溯到所提供的预算约束

### 用例 6：缺少门禁输入——NOT ASSESSED
**场景：** 一份 `InventorySystem` 实现被提交代码审查，包含其实现文件、其故事的验收标准和其管辖 ADR；Agent 能检查的一切都健全。门禁指定的相关 GDD 章节未被传递：上下文既未给出其文本也未给出路径，故事文件未指定任何内容，调用技能也未报告其缺失。请求标记为 LP-CODE-REVIEW。
**预期：** 对 LP-CODE-REVIEW 返回 NOT ASSESSED，指定 GDD 章节为其未获得的输入——没有它，门禁对 GDD 规则正确性问题的检查无法进行，因此 APPROVE 无法达成。
**断言：**
- [ ] 对 LP-CODE-REVIEW 明确陈述裁决 `NOT ASSESSED`——而非 APPROVE，尽管它能检查的一切都健全
- [ ] 指定相关 GDD 章节为缺失输入
- [ ] 不从代码或故事推断 GDD 规则并据此判断正确性
- [ ] 变体——若调用技能报告不存在库存 GDD，那是发现，而非缺失输入：裁决为 CONCERNS 或 REJECT，而非 NOT ASSESSED

## 协议合规

- [ ] 仅使用 APPROVE / CONCERNS / REJECT 词汇返回 LP-CODE-REVIEW 裁决——或当门禁指定的输入未给出或无法读取时，使用 `NOT ASSESSED` 并指定输入；调用技能报告缺失的构建产物是发现，以门禁自身的措辞表述
- [ ] 仅使用 FEASIBLE / CONCERNS / INFEASIBLE 词汇返回 LP-FEASIBILITY 裁决——或当门禁指定的输入未给出或无法读取时，使用 `NOT ASSESSED` 并指定输入；调用技能报告缺失的构建产物是发现，以门禁自身的措辞表述
- [ ] 保持在声明的代码架构领域内
- [ ] 将设计优先级冲突交由 creative-director
- [ ] 将每个门禁裁决陈述为该门禁定义中的明确裁决词，而非内联叙述隐含的裁决
- [ ] 不做出有约束力的游戏设计或创意方向决策
