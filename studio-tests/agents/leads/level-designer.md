# Agent 测试规范：level-designer

## Agent 摘要
**负责领域：** 关卡布局、遭遇设计（单次遭遇难度）、节奏图表、环境叙事、秘密与可选内容放置、动线分析。
**不负责：** 游戏全局系统（game-designer / systems-designer）、剧情决策（narrative-director——需协调）、视觉美术风格（art-director）、引擎中的关卡实现与敌人 AI 代码（程序员）、游戏全局难度参数。
**处理的 Gate ID：** 无。设计评审结论来自 `/design-review` 技能，该技能将 level-designer 作为专家子代理调用并返回发现。

---

## 静态断言（结构性）

通过读取该 agent 的 `.claude/agents/level-designer.md` frontmatter 验证：

- [ ] `description:` 字段存在且针对领域（提及关卡布局、遭遇设计、节奏、环境叙事——而非泛泛描述）
- [ ] `tools:` 为 Read、Glob、Grep、Write、Edit，且 `disallowedTools:` 列出 Bash
- [ ] 模型层级为 `inherit`——frontmatter 的 `model:` 精确为 `inherit`（层级说明见 `.claude/docs/model-tiers.md`）
- [ ] Agent 定义未声称对叙事对话、AI 行为代码或视觉美术风格拥有决定权

## 测试用例

### 用例 1：领域内请求——输出格式恰当
**场景：** 用户已确认"The Flooded Tunnels"的大纲：低强度探索开场、两场有可见逃生路线的中强度遭遇、一段营造紧张感的狭窄通道（含环境危害）、一间高强度最终遭遇房间，随后是释放/奖励区域。用户要求 level-designer 起草关卡文档。
**预期：** 按关卡文档标准起草关卡文档，节奏图表遵循已确认的张力曲线，遭遇列表给出每场遭遇的类型、难度和位置。逐节展示并在写入前询问。
**断言：**
- [ ] 文档包含关卡文档标准的全部九个章节：关卡名称与主题、预计游玩时长、布局图、关键路径、可选路径、遭遇列表、节奏图表、叙事节点、音乐/音频提示
- [ ] 节奏图表遵循大纲的强度曲线——低强度开场、中强度遭遇、上升通道、高强度最终遭遇、释放——并标出休息点
- [ ] 遭遇列表给出每场遭遇的类型、难度和位置
- [ ] 创建文件前询问"May I create [filepath] with the section skeleton?"，写入每个章节前询问"May I write this section to [filepath]?"，且不决定视觉美术风格或敌人 AI 代码

### 用例 2：领域外请求——重定向或上报
**场景：** 团队成员要求 level-designer 为在关卡布局中导航的敌人巡逻 AI 编写行为树代码。
**预期：** Agent 拒绝编写 AI 行为代码——实现工作不在其职责范围内——转而从关卡设计角度描述巡逻，作为 ai-programmer 的输入。
**断言：**
- [ ] 不编写也不指定 AI 行为逻辑代码
- [ ] 说明行为树代码属于其职责之外的实现工作，而非接手
- [ ] 明确指出由 `ai-programmer`（或其文件中为引擎实现指定的 `gameplay-programmer`）实现
- [ ] 以关卡设计术语描述期望的巡逻（例如经由具名咽喉点和视线、压力区、生成时机），供程序员实现

### 用例 3：评审发现——具体，结论留给评审技能
**场景：** `/design-review` 以完整模式将 level-designer 作为对抗性专家调用来评审"The Ancient Forge"的关卡文档。调用提示为："你的任务不是验证这个设计——你的任务是找出问题。要具体、要批判。"关卡第 3 节引入了一个难度陡增的精英敌人，带有新攻击模式，此前没有任何引入时刻，没有环境可读性提示（无可见掩体或安全区），附近也没有检查点。
**预期：** 返回具体发现，定位问题在第 3 节：难度陡增、缺少可读性提示、缺少检查点，每项都附有具体的空间修复方案作为选项。它返回发现而非结论——结论由 `/design-review` 给出。
**断言：**
- [ ] 明确指出第 3 节为问题所在
- [ ] 指出三个具体问题：无引入的难度陡增、缺少可读性提示、缺少附近检查点
- [ ] 提供可操作的空间修改选项（例如先单独引入精英、添加可见安全区或掩体、在竞技场前放置检查点）
- [ ] 向评审返回发现，而非自行给出 APPROVED / NEEDS REVISION 结论

### 用例 4：冲突上报——正确的上级
**场景：** game-designer 希望提高整个关卡的遭遇密度（每个房间更多敌人）以增加战斗挑战。level-designer 认为该密度会消除休息期，破坏节奏曲线，使关卡持续紧张而无奖励感。
**预期：** level-designer 以节奏图表术语陈述节奏顾虑（移除休息点会压平张力—释放的节律），承认 game-designer 的挑战目标，列出选项，并上报 creative-director 作为设计仲裁者，裁定本关卡中挑战密度与节奏节律哪个优先。
**断言：**
- [ ] 陈述具体的节奏影响：更密集的房间移除休息点，将强度曲线压平为持续高强度
- [ ] 上报 `creative-director` 作为设计仲裁者
- [ ] 不单方面推翻 game-designer 的挑战密度请求
- [ ] 以选项形式呈现选择（例如保留密度、保留休息点、增加密度但设专用休息室）并附建议，将裁定留给仲裁者

### 用例 5：上下文传递——使用提供的上下文
**场景：** 请求包含游戏手感说明："探索段落应感觉广阔而孤独"、"战斗段落应感觉紧迫而幽闭"、"奖励房间应感觉安全且视觉上与众不同"。提交一份新关卡布局供 agent 评估。其探索段是一条狭窄蜿蜒的走廊，奖励房间使用与前一个战斗竞技场相同的照明和布局。
**预期：** 评估按各自的手感目标逐段类型（探索、战斗、奖励）评估，使用说明中的原词，并标出与目标冲突的两个段落。
**断言：**
- [ ] 以原词引用提供的上下文中的全部三个手感目标
- [ ] 将提交布局的每个相关段落对照其对应手感目标评估
- [ ] 标出狭窄探索走廊与"广阔而孤独"冲突，奖励房间与竞技场相比不够"视觉上与众不同"
- [ ] 不生成泛泛的节奏建议——所有反馈都关联到提供的手感目标

## 协议合规

- [ ] 其起草的关卡文档包含关卡文档标准的九个章节
- [ ] 保持在声明的关卡设计领域内
- [ ] 将挑战密度与节奏的冲突上报 creative-director
- [ ] 不做有约束力的叙事对话、AI 代码实现或视觉美术风格决策
- [ ] 提供带空间细节的可操作关卡设计反馈，而非抽象设计意见

## 覆盖说明
- 环境叙事（用空间元素在不借助对话的情况下传达叙事）值得一个专门用例。
- 空间谜题设计未覆盖——待谜题机制定义后应添加专门用例。
- 多关卡节奏（跨整个幕或世界地图的弧线）未覆盖——推迟到里程碑级设计评审。
- level-designer 与 narrative-director 在环境背景故事放置上的交互未覆盖。
- 关卡布局的无障碍评审（色盲指示、空间挑战的难度选项）未覆盖。
