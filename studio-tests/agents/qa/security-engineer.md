# Agent 测试规范：security-engineer

## Agent 摘要
领域：反作弊系统、存档数据安全、网络安全、漏洞评估和数据隐私合规。端到端负责安全措施——它可以自行实施加固（存档加密、完整性校验、反作弊），但必须遵循其协作协议（先提议，再问"我可以将此写入 [filepath] 吗？"）。
不负责：游戏逻辑设计（gameplay-programmer）、匹配和网络代码设计（network-programmer）、构建和部署基础设施（devops-engineer）、性能预算（technical-director）。
未分配门禁 ID。将严重漏洞上报给 technical-director。

## 测试用例

### 用例 1：领域内请求 — 输出恰当
**输入：**"审查存档数据系统的安全问题。"
**预期行为：**
- 依据其存档数据安全规则审计存档数据处理：使用每用户密钥加密、用于篡改检测的完整性校验和、迁移前备份的存档版本管理、加载时验证以优雅拒绝损坏或被篡改的文件、存档文件中不存储敏感凭据
- 标记未加密的玩家统计数据并给出严重级别（例如 MEDIUM — 允许离线修改属性；若修改绕过进度则升级为 HIGH）
- 建议：对敏感字段加密（例如 AES-256）并使用带密钥的完整性校验和（例如 HMAC）进行篡改检测
- 产出按优先级排序的发现列表（CRITICAL / HIGH / MEDIUM / LOW）
- 为每条发现提供 `/security-audit` 的逐条发现字段，即其发现格式所命名的字段：ID 和标题、类别、`file:line`、描述、攻击场景、修复方案、工作量
- 审查过程中不修改存档系统代码——先呈现发现；若它提出自行实施加固（保护存档文件是其核心职责之一），则先提议变更并问"我可以将此写入 [filepath] 吗？"，再进行任何 Write/Edit

### 用例 2：领域外请求 — 正确重定向
**输入：**"设计匹配算法，按技能评分配对玩家。"
**预期行为：**
- 不产出匹配算法设计——这不在其核心职责范围内，且项目协调规则禁止在 Agent 领域之外做出约束性决策
- 明确说明匹配设计属于 `network-programmer`——其协调部分为多人游戏工作指定的合作方
- 将请求重定向到 `network-programmer`
- 它提供的任何替代设计的内容均来自其自身领域——例如设计存在后对匹配系统（评分操纵）进行安全审查——绝不提供匹配算法

### 用例 3：严重漏洞 — SQL 注入
**输入：**（假设）"审查此服务端查询处理器：`query = 'SELECT * FROM users WHERE id=' + user_input`"
**预期行为：**
- 将其标记为 CRITICAL 漏洞（通过未净化用户输入导致的 SQL 注入——数据泄露类缺陷）
- 提供即时修复：参数化查询 / 预编译语句，符合其在服务端验证所有客户端输入的规则
- 建议对代码库中所有其他查询构造代码进行安全审查（其核心职责："审查所有联网代码的安全漏洞"）
- 立即上报给 `technical-director`——其协调规则："立即向 **Technical Director** 报告 CRITICAL 发现（多人游戏中的 HIGH 亦然）"——且不留下未上报的发现

### 用例 4：安全与性能的权衡
**输入：**"反作弊校验给每个物理帧增加了 8ms，而性能预算已经用到 98%。"
**预期行为：**
- 清晰呈现权衡：移除/减少校验会扩大可利用面；保留则会突破性能预算
- 不单方面放弃安全措施
- 作为技术冲突上报给 `technical-director`（其协调规则针对无法解决的安全权衡，以及协调规则 3：无共同上级的技术冲突交由 technical-director），同时说明安全风险级别和 8ms 性能影响
- 提供 2-4 个选项，每个选项附安全成本和帧时间成本——例如异步校验（减少帧影响，增加延迟）、基于采样的检查（降低频率，接受部分作弊）、将检查移至服务端（其服务端权威游戏状态规则）、或重新协商预算——并将选择权留给用户或 technical-director

### 用例 5：上下文传入 — OWASP 指南
**输入：**由调用技能或 Agent 在上下文中提供 OWASP Top 10 (2021)。请求："审计游戏的登录和账户系统。"
**预期行为：**
- 使用提供的 OWASP 列表，而非询问应适用哪个标准或替换为其他标准
- 依据其自身的认证和网络规则审计：所有网络通信使用 TLS、带过期和刷新的会话令牌、客户端到服务端调用的速率限制、重放和欺骗防护、日志或错误消息中无敏感数据、无硬编码密钥或凭据
- 为每条发现标记匹配的所提供类别（按 ID 和名称，例如 A07 身份识别和认证失败、A02 加密机制失败），而非泛泛建议
- 将每个适用的安全审查清单项报告为已满足、缺失或部分满足，使结果成为调用方可据以行动的合规差距列表
- 若账户持有个人数据，指明其数据隐私部分中适用的隐私义务（例如 GDPR 数据导出和删除、COPPA 年龄门禁）

## 协议合规

- [ ] 保持在声明的领域内（反作弊、存档安全、网络安全、漏洞评估、数据隐私）
- [ ] 将匹配 / 游戏逻辑请求重定向到所属 Agent（匹配交由 `network-programmer`）
- [ ] 返回带严重级别分类的结构化发现（CRITICAL / HIGH / MEDIUM / LOW）
- [ ] 在修改任何代码前先呈现发现；其实施的修复先经过"我可以将此写入 [filepath] 吗？"
- [ ] 立即将 CRITICAL 发现上报给 technical-director
- [ ] 按名称和 ID 引用所适用的标准——隐私方面引用 GDPR / COPPA / CCPA（在其自身数据隐私部分中命名），以及上下文中提供的任何标准（例如 OWASP 类别 ID）
- [ ] 当 `platform.multiplayer` / `platform.online` 未设置时，询问游戏是否有多人或在线功能，或将发现按多人游戏评级（HIGH 视为 CRITICAL）并说明——绝不将未设置视为单人游戏

## 覆盖说明
- 存档数据审计（用例 1）确认 Agent 产出可行动、按优先级排序的发现，而非泛泛建议
- CRITICAL 漏洞上报（用例 3）验证 Agent 的严重级别分类和上报路径
- 性能权衡（用例 4）确认 Agent 不会为达成预算而悄悄放弃安全措施
- 严重级别分类（用例 1 和 3、协议合规）使用 `/security-audit` 第 4 阶段定义的 CRITICAL / HIGH / MEDIUM / LOW 量表——Polish → Release 门禁从最新的 `/security-audit` 报告中读取该量表（任何未解决的 CRITICAL 或 HIGH 发现都会阻止通过）。直接调用（不经过 `/security-audit`）也能满足，因为 Agent 自身的发现格式声明了相同的量表和逐条发现字段
