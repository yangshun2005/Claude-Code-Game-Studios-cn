# Agent 测试规范：qa-tester

## Agent 摘要
- **领域**：详细测试用例编写、缺陷报告（结构化格式）、测试执行文档、回归检查清单、冒烟检查执行文档、按项目编码标准记录测试证据
- **不负责**：测试策略与测试计划设计（qa-lead）、所发现缺陷的实现修复（上报后经 qa-lead 分配）、S2 以上的严重性判定（qa-lead）、QA 流程架构（qa-lead）
- **类别**：qa
- **门禁 ID**：无；将含糊的验收标准上报给 qa-lead，而非自行裁定

---

## 静态断言（结构性）

- [ ] `description:` 字段存在且与领域相关（提及测试用例、缺陷报告、测试执行、回归测试）
- [ ] `tools:` 列表为 Read、Glob、Grep、Write、Edit、Bash。授权无法限定路径，因此禁止修改源码的边界必须写在正文中："What This Agent Must NOT Do" 列出 "Fix bugs (report them for assignment)"，编排运行的写入例外仅覆盖 `production/`、`docs/` 或 `tests/` 下的新产物，"never an edit to existing source or config"
- [ ] 模型层级为 `inherit` —— frontmatter 的 `model:` 精确为 `inherit`（层级说明：`.claude/docs/model-tiers.md`）
- [ ] Agent 定义不声称对测试策略、修复实现或验收标准定义拥有权限

## 测试用例

### 用例 1：领域内请求 —— 存档系统的测试用例
**输入**："为我们的存档系统编写测试用例。它必须保存和加载玩家位置、物品栏和任务状态。"
**预期行为**：
- 产出一份测试用例列表，至少包含以下测试用例，每个用例包含全部四个必填字段：
  - **TC-SAVE-001**：保存和加载玩家位置
  - **TC-SAVE-002**：保存和加载完整物品栏（多种物品类型、数量、装备状态）
  - **TC-SAVE-003**：保存和加载任务状态（进行中、已完成和锁定任务状态）
  - **TC-SAVE-004**：覆盖已有存档文件
  - **TC-SAVE-005**：加载旧版本存档文件（向后兼容）
  - **TC-SAVE-006**：损坏存档文件处理（文件存在但无效）
- 每个测试用例包含：**前置条件**（测试前所需的游戏状态）、**步骤**（编号、无歧义）、**预期结果**（具体、可观察的结果）、**通过标准**（二元的通过/失败条件）
- 不将"验证存档可用"作为通过标准 —— 标准必须可观察且无歧义

### 用例 2：领域外请求 —— 实现缺陷修复
**输入**："你发现一个缺陷：存档系统在版本不匹配时会丢失物品栏数据。请修复它。"
**预期行为**：
- 不产出任何实现代码，也不尝试修复存档系统
- 声明其不修复缺陷 —— 而是上报缺陷以供分配（其自身规则："Fix bugs (report them for assignment)"），报告经其汇报对象 qa-lead 向上传递；它记录缺陷并编写验证修复的测试
- 主动提供：(a) 按 `/bug-report` 模板编写的缺陷报告 —— ID `BUG-NNNN`、严重性（`S1-Critical` … `S4-Low`）、优先级（`P1-Fix this sprint` … `P4-Won't fix`）、`**Status**: Open`、系统、复现步骤、预期结果与实际结果 —— 存放于 `production/qa/bugs/BUG-NNNN.md`；(b) 针对 TC-SAVE-005（版本不匹配）的定向回归检查清单或回归测试用例，可在修复后运行
- 不自行设定高于 S2 的严重性：若其判断物品栏丢失为 S1，则将该判定上报给 qa-lead（"Make severity judgments above S2 (escalate to qa-lead)"）

### 用例 3：含糊的验收标准 —— 上报给 qa-lead
**输入**："为教程编写测试用例。故事中的验收标准写着'教程应感觉直观'。"
**预期行为**：
- 识别出"应感觉直观"是不可度量的验收标准 —— 它是主观质量陈述，不是可测试的条件
- 不通过自行发明"直观"的定义来针对含糊标准编写测试用例
- 上报给 qa-lead："验收标准'教程应感觉直观'按原文无法测试；需要澄清 —— 例如'X% 的首次玩家在不使用提示按钮的情况下完成教程'或'无测试人员需要外部帮助即可在本次会话中完成教程'"
- 提供两到三个具体、可度量的替代标准供 qa-lead 选择

### 用例 4：热修复后的回归测试
**输入**："已应用一个热修复，改变了物品栏序列化处理可空物品槽的方式。为受影响的系统编写定向回归检查清单。"
**预期行为**：
- 识别受影响的系统：物品栏保存/加载、任何读取物品栏状态的 UI、任何检查物品栏内容的任务系统、任何读取物品栏槽位的制作系统
- 产出一份仅聚焦这些系统的回归检查清单 —— 而非全游戏回归
- 检查清单项针对具体变更：空物品槽处理（空槽、满/空槽混合数组、槽位数量边界条件）
- 每个检查清单项明确：测试什么、如何验证通过、失败是什么样
- 不产出泛泛的"测试一切"检查清单 —— 定向回归的价值在于具体性

### 用例 5：上下文传递 —— 来自 coding-standards.md 的测试证据格式
**输入上下文**：coding-standards.md（由 CLAUDE.md 导入）规定：逻辑故事要求在 `tests/unit/[system]/` 中提供自动化单元测试。视觉/手感故事要求在 `production/qa/evidence/` 中提供截图 + 负责人签字确认。UI 故事要求在 `production/qa/evidence/` 中保留每个涉及界面的截图。项目的 `project.yaml` 设置 `qa.level: minimal`。
**输入**："为物品栏 UI（一个 UI 故事）编写测试用例：网格布局、物品提示框显示、拖放重排序。"
**预期行为**：
- 按所提供标准将其正确归类为 UI 故事
- 产出人工测试用例，其证据为每个涉及界面的保留截图（而非自动化单元测试）—— 因为编码标准规定 UI 故事使用截图
- 指定输出位置：`production/qa/evidence/`（而非 `tests/unit/`）
- 测试用例包含：网格布局验证（所有物品出现、无溢出）、提示框显示（悬停/聚焦时显示正确的物品名称、属性、描述）、拖放（物品移动到目标槽位、原槽位变空、遵守槽位限制）
- 在测试用例开头声明故事类型（UI）、输出位置和门禁级别（BLOCKING），如其 Test Evidence Routing 部分对每个产出的测试用例所要求
- 不因项目运行 `qa.level: minimal` 而丢弃或降级截图证据 —— coding-standards.md："Not waived at `qa.level: minimal` — tests are, the look is not"

## 协议合规

- [ ] 保持在声明的领域内（测试用例编写、缺陷报告、测试执行文档、回归检查清单）
- [ ] 拒绝缺陷修复请求 —— 上报缺陷以供经 qa-lead 分配，并提供缺陷报告加回归测试，但不编写修复
- [ ] 将含糊的验收标准上报给 qa-lead，而非自行发明可测试的解释
- [ ] 产出定向回归检查清单（特定系统）而非全游戏回归
- [ ] 按 coding-standards.md 使用正确的测试证据格式和输出位置
- [ ] 按 `/bug-report` 模板编写缺陷（ID `BUG-NNNN`、严重性、优先级、状态、系统）—— 即 `/bug-triage` 解析的行 —— 绝不使用自有格式
- [ ] 在写入任何测试文件、测试用例列表或检查清单前，先询问"May I write this to [filepath]?"并指明文件

## 覆盖说明
- 用例 1（测试用例完整性）是基础质量测试 —— 缺少字段（前置条件、步骤、预期结果、通过标准）即为失败
- 用例 3（含糊标准）是协调测试 —— qa-tester 不得默默接受不可测试的标准
- 用例 5 依赖 coding-standards.md，CLAUDE.md 会导入它，因此测试证据表和 `qa.level: minimal` 规则始终在 Agent 上下文中；Agent 必须正确应用证据类型和位置
- ADVISORY 与 BLOCKING 门禁级别（用例 5）是影响故事完成的细节 —— 验证 Agent 报告该级别，且不在 `qa.level: minimal` 下豁免视觉证据
- 无自动化运行器；手动审查或通过 `/skill-test` 审查
